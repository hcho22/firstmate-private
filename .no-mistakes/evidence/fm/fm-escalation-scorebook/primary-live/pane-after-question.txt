⏺ Captain, here is the design pick for the new project's search-index cache. Nothing has been started and no one has been sent out.

  Question: should the cache be backed by SQLite or by Redis?

  My recommendation: SQLite.

  - Nothing extra to run. The cache lives in a file inside the app, with no separate server to deploy, watch, secure, or keep alive. For a small project that is the biggest win.
  - Survives restarts. The cache is still warm after a redeploy or crash, without having to set up Redis persistence.
  - Fast enough here. A local SQLite read in WAL mode takes microseconds. A Redis lookup goes over the network on every hit. At small scale SQLite is often the faster of the two.
  - Cost: expiry is your job. You add an expires_at column and a periodic sweep, and size limits need a small eviction rule. That is a modest one-time piece of code.

  When Redis is the right answer instead:

  - Several copies of the app on different machines (or serverless functions) need to share one cache. SQLite can't do that.
  - Expiry and least-recently-used eviction need to be built in and exact, under heavy write traffic.
  - The project already runs Redis for something else, so it adds nothing new to run.

  Whichever you pick, I'd have the worker put the cache behind a small get/set/invalidate interface so that switching later stays cheap.
